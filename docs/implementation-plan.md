## Phase 2 — Educational engine (Days 1–2)
Pure Dart package `src/engine` (`bousla_engine`), no Flutter or Firebase dependency.

6. Resource recommendation (approved only; preferred language first).

## Phase 7 — AI level 2: explanations on top of the engine (Day 5)
- Prompt builders and output guards in the engine package (pure Dart, unit-tested): known concepts only, approved resource IDs only, requested language, no definitive diagnostic wording.
- Student: personal explanation + short learning plan. Instructor: suggested teaching action.
- Template fallback on model failure or guard failure; "AI-generated" label next to the evidence.
- Evaluation: ~20 synthetic evidence cases in AR and EN; report the real guard pass rate.
Deliverable: grounded, guarded, measured AI explanations.

Status (24 Nov, student explanations — Lina): **implemented with guards and template fallback; verified with unit tests and a mocked model only. Not yet run against Gemini; the instructor teaching suggestion is not done.**
- Engine (`src/engine/lib/src/ai/feedback_explanation.dart`, pure Dart, exported from `bousla_engine.dart`): anonymous profile per student (concept names, states, attempt/correct counts, student-facing prerequisite signals, recommendations with approved resource IDs and titles; no UID, name, answers, keys or URLs); identical profiles merged by a canonical signature (`groupProfiles`, IDs `p1…` independent of student order; the same state with different counts is not merged); one prompt + JSON schema for the whole class (`[{profile_id, text_ar, text_en}]`, 2–4 sentences, ≤ 600 characters); parsing; five guards; a deterministic bilingual template. `stripCodeFence` moved to `ai/model_json.dart` (shared with question drafting, unchanged behaviour).
- Guards, each a public function with valid and invalid tests: 1 concepts (no other course concept named, AR or EN, in either text, tolerant of Arabic prefixes; no foreign concept/resource ID); 2 resources (links must be a profile resource's URL; no unknown `res_…`; no title of another course resource); 3 language (`text_ar` Arabic, at least half its letters; `text_en` no Arabic); 4 wording (Arabic and English lists, e.g. لديك فجوة، لا تفهم، مستواك ضعيف، you have a gap, you failed, weak, definitely; matched after removing diacritics and case); 5 length (non-empty, ≤ 600). Any failure, a missing entry or an unreadable answer → that profile gets the template. Limit of guard 1: a topic in neither the course nor the profile cannot be recognised by name.
- App: `FeedbackExplainer` + `GeminiFeedbackExplainer`, built like `GeminiQuestionGenerator` (same models and fallback, `callWithModelFallback`, busy/quota/daily-quota handling); the Gemini error mapping became a shared `withGeminiErrors` (no behaviour change). One request per publication; never when a student opens feedback.
- 20-profile harness (`src/engine/test/feedback_explanation_eval_test.dart`): 26 synthetic students (6 patterns answered twice, once in each language) → 20 unique profiles in ONE mocked request. The mocked answer is a fixture: 12 entries written to be acceptable and 8 with typical mistakes. Measured: **12 of 20 accepted (60%)**; all 12 acceptable entries passed (no false rejections) and all 8 faulty ones were caught, each for the expected reason (unknown concept ×2, invented link, English in `text_ar`, forbidden wording ×2, too long, missing entry → template). This measures the guards against the fixture, **not Gemini's quality**; the live pass rate is still unmeasured.
- Verified (cloud environment, Flutter 3.38.10 / Dart 3.10.9): `dart analyze` clean and `dart test` **99/99** in `src/engine`; `flutter analyze` clean and `flutter test` **153/153** in `src/app`; rules emulator tests **32/32** (`cd firebase && npm test`). The cloud Flutter re-resolves `pubspec.lock`; that change was not kept. To run on a developer machine: `dart pub get && dart test` in `src/engine`, then `.\bousla test`.

## Staged after the competition (kept, not removed)
- Persistent learning profiles via optional account linking (`architecture.md` §10). Agreed design (24 Nov): the student may sign in to keep their history, but **answering stays anonymous to the instructor**: the session flow, rules and aggregated instructor views do not change. Signing in links the anonymous account to Google or a university email (`linkWithCredential`), keeping the same UID, so earlier answers made in that browser become part of the student's own profile for their personal analysis (progress across sessions, recurring possible gaps). Before building: consent text, a way to see and delete one's profile, and rules so only the student reads `profiles/{uid}`. Linking only covers sessions answered in the same browser before signing in.
- Longitudinal progress across sessions.
- Career pathways and skill-gap analysis. Needs real, sourced data mapping concepts to job skills (e.g. from job postings or a published framework); no figures may be invented for the demo. Note (24 Nov): `data/careers/backend-developer.json`, named here earlier, does not exist in the repository.
- Multilingual free-text AI evaluation, only after a rubric, labeled AR/EN/mixed test set, abstention and consistency tests exist.
- Storing uploaded files and file resources (Cloud Storage, Blaze plan).
- Server-side scoring (Option B) for instant feedback.
